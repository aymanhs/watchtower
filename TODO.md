# Watchtower — status

Phases per the original project brief. Check `git log` for commit-level detail; this is the glanceable summary.

## Phase 1 — Prove the collection engine ✅ done

- YAML metric definitions, YAML server configs, SSH connection, shell collector, line-oriented `key=value` parsing, namespaced timestamped observations.
- Proven live against two real lab servers.

## Phase 2 — Scheduling and generic metrics ✅ done

- Per-metric/per-server scheduling, independent goroutines (`internal/scheduler`), bounded global concurrency.
- Group-based metric selection (`metric.Registry.ResolveGroups`).
- Full override precedence chain: **definition default → group config (`internal/group`, order-deterministic by the server's own group list) → server-specific override**, all via `metric.Definition.Resolve`.
- Collection failure isolation — one server/metric failing never affects another.
- Bug found & fixed along the way: SSH connections now warm up concurrently at start-up so a cold dial never eats a metric's own command timeout.

## Phase 3 — Storage 🟡 engine done, chart UI not built yet

- `internal/storage` — built after actually reading NanoTDB's design (`~/code/nanotdb`, docs/CONCEPTS.md), not guessing or reinventing blind. Deliberately much smaller: at this project's scale (a handful of servers, a few dozen metrics, 5s-60s intervals) NanoTDB's WAL-for-flash-wear, page compression, multi-database namespacing, and precomputed rollups solve problems that don't exist here. Kept, because they earn their place at any scale: one append-only file per UTC day (`data/storage/data-YYYY-MM-DD.dat`, fixed 18-byte records — `uint16` metric ID + `int64` ns timestamp + `float64` value, no compression), a small JSON catalog (name ↔ ID), retention as plain file deletion.
- **No WAL, on purpose** — every `Append` is synced before it returns, so there's no separate durability structure to ever need recovering; a reopened `Store` just sees whatever was already durable. At NanoTDB's target scale (many writes/sec on a Pi's SD card) that would be real flash wear; at ours (≈1 write/sec across *all* metrics combined) it isn't. Proven, not assumed: a dedicated test closes a `Store`, reopens a fresh one pointed at the same directory, and confirms the data is there with no replay step.
- Rollups: skipped for v1 by design, not forgotten — MyGo's own `ui/chart` package ships a `MinMax` downsampler built exactly for rendering (reduces to one min/max pair per pixel column of the plot), so raw points + render-time downsampling covers the chart use case without a background rollup job. Revisit only if a query ever actually gets slow at real data volumes.
- Wired into `internal/app.MetricTask` as an optional `History *storage.Store` field (nil for console — GUI-only for now, by choice, same nil-vs-real pattern `Store` already used for state): a storage error is logged, never treated as a collection failure — persisting history and collecting successfully are different concerns.
- 19 new tests (`internal/storage` + 2 in `internal/app`), confirmed live end to end: ran the real GUI against jumpbox/sbnats, confirmed real `.dat`/`catalog.json` files appeared, then queried them back with a standalone program and got the real recorded point with its real timestamp.
- **Chart UI built** — third bottom-panel mode (`"chart"`, alongside events/terminal), triggered by a small trending-icon on each metric line (`chart.go`'s `chartIcon`). Picks the metric's `Primary` measurement if it has one, else the first by key. Renders with MyGo's real `ui/chart` (`Plot`, `NewTime`/`NewLinear` scales, `Line`, `Extent`) — the same `StrokePath`-on-a-`Painter` pattern the gauges already use, just a path `chart.Line` builds instead of a hand-rolled one.
- **Counters are charted as a rate, not raw** — a real issue caught live, not in review: `network.rx_bytes` charted raw is just an ever-climbing line (it's cumulative bytes since boot). Added `state.MeasurementView.Type` (the measurement's own gauge/counter/rate, previously not threaded through to the GUI at all) so the chart can tell, and `rateOf` converts a counter's points to bytes/sec (or whatever/sec) before plotting, clamping a negative delta — a counter reset, e.g. a reboot — to 0 rather than showing a bogus negative spike. 4 new tests.
- One more real thing caught live, not assumed: the first chart looked wrong (an old high plateau dwarfing recent data) — traced to literal test-data pollution from this session's own repeated manual launches (one stretch was me running the terminal-plugin test, which opened 8 simultaneous SSH connections at once) by actually querying the raw stored points and their inter-sample rates, not by guessing. Confirmed it was test noise, not a bug, then cleared `data/storage/` so real history starts clean from here.
- **Closed: multi-series, dual-axis charting** — a metric's chart now plots *every* measurement, not just the primary one. Grouped by `Unit` (`groupByUnit` in `panel.go`): measurements sharing a unit share a y-axis, the primary's unit group goes left, the next distinct unit (if any) goes right — confirmed via direct reading of MyGo's `ui/chart` source that `chart.Plot`'s `Axes{Left, Right}` supports both simultaneously and multiple `chart.Line` draws can share one `Draw` callback. Capped at 2 groups (`Axes` has no more than Left/Right); each individual series gets its own color from a small fixed categorical palette (`seriesColors`) and a legend row (colored dot + label + unit) above the plot. Per-series counter→rate conversion (`rateOf`) now happens per-measurement inside the group, not once for the whole metric. The click handler (`view.go`'s `metricLine`) only records *which metric* was clicked now (`chartServer`/`chartMetric`) — which measurements/units/counters it has is re-derived fresh from the live snapshot every render in `chartPanel`, same "always reflects current reality" pattern as everything else here. Confirmed live against jumpbox's real `cpu` metric: `load1`/`load5`/`load15` (unit `load`) render together on the left axis, `usage` (unit `percent`) on the right, each its own color, legend correct.
- **Closed: chart axis labels and the plain metric line both humanize large numbers now** — raw huge values (a disk chart's right y-axis showing `35000000000`, a metric line showing `rx_packets=13972777.00`) were exactly the same unreadable-big-number problem the original `rx_bytes` counter chart had, just not counter-related this time. `formatValue` (view.go) now scales *any* large value, not just bytes: bytes still get GiB-scaled, anything else gets K/M/B-scaled generically (so `count`-unit measurements like packet totals read as `13.97M`). Reused on chart axes too — `chart.Linear.Format` (a hook the library already exposed, found by reading `ui/chart/scale.go`) is set per unit-group to the same `formatValue`, so a group's y-axis ticks read `39.7GiB` instead of raw bytes. New tests (`TestFormatValue_HumanizesLargeCounts`). Confirmed live against jumpbox's real `network` and `disk` metrics.
- **Closed: gauge marker is now a needle, not a dot** — `pressureGauge` (gauge.go) draws a thin hand from the center out to near the band (with a small hub at the center) instead of a filled circle sitting on the band; drawn before the center label `Child`, so it reads as behind the number, not overlapping it. Colored `t.TextMuted`, deliberately not `t.Text` (the center label's own color) — caught live: with both the same color, the needle and the number blurred into one shape rather than reading as two things. Confirmed live.
- **Fixed a real bug the multi-series work introduced: `groupByUnit` was dropping the actual loads.** Non-primary unit groups were ordered alphabetically-only, so for cpu (usage=percent/primary, load1/load5/load15=load, cores=count — cores being just a scaling reference for the load bars, not something anyone charts on its own) the 1-member "count" group beat the 3-member "load" group alphabetically for the second axis slot, silently dropping load1/load5/load15 — the entire reason this feature exists. Caught live via a real sbnats chart showing only usage+cores. Fixed: non-primary groups now sort by member count (descending) first, alphabetical only to break ties. New regression test reproduces the exact cpu.yaml shape.
- **Closed: chart now has faint grid lines and an axis-colored legend.** Grid lines (`t.Border.Alpha(0.5)`) draw behind the data from the left axis's and the time axis's own ticks — found via `chart.Y`/`chart.X`, exactly the pattern `ui/chart`'s own package doc comment shows. The legend no longer reads as a flat list of colored dots: it's grouped by axis side ("Left axis (unit)" / "Right axis (unit)"), each heading tinted to match that axis's own first series' color, and the axis's own tick labels (`chart.Axes.Label`) get the same tint — answers "which line reads which axis" by color, not by inferring it from position. Confirmed live against sbnats's real cpu chart (3 load lines + usage, left/right correctly distinguishable).
- **Added `display.format`** (`int`/`human`, `internal/metric/display.go`) — a declarative hint for how the GUI prints a measurement's number, same principle as `Widget`: never guessed from a value's magnitude, always read from the definition. `FormatInt` drops decimals (docker's container/image counts: "3", not "3.00"); `FormatHuman` K/M/B-scales a large value (network's packet counters: "13.97M", not "13972777.00"). `formatValue` (view.go) uses it for both a metric line's plain-text values and (always as `FormatHuman`, since a tick is a big round number by construction regardless of what the underlying measurement declares) chart axis labels. Confirmed live.
- Still open: no window picker (fixed at 1 hour — `chartWindow` in `panel.go`), no way to choose which 2 unit-groups chart if a metric has more than 2 distinct units (biggest-group-first-then-alphabetical now, but still silently drops the rest beyond 2).

## Phase 5 — Native GUI 🟡 first PoC done

- `cmd/watchtower-gui`: real MyGo native-UI window, built on the exact same engine as the console (`internal/app.Bootstrap` shared by both binaries — the console binary was slimmed down to a thin caller of it in the process).
- `internal/state`: the "Application API / data model" layer (brief #8) — a thread-safe `Store` holding each server's current metric status, read via `Store.Snapshot()`. GUI-agnostic; console binary doesn't use it (`Store` is nil there).
- Adaptive layout by window width (`cmd/watchtower-gui/view.go`), three tiers, confirmed live by resizing the actual window: compact (dot + server name) → medium (+ one dot per metric) → detailed (+ each metric's measurements and values).
- Green/amber/red/grey status (`state.Status`): grey (`StatusUnknown`) is a first-class state, not a bug — a collector failure marks the metric stale **without discarding its last-known value** (`Store.MarkStale`), satisfying the brief's "last-known values remain available but are clearly marked stale" requirement directly.
- Proven live against two real lab servers via WSLg (real window on the real desktop, not a screenshot).
- Dark mode: automatic (MyGo follows the OS by default; every color comes from `c.Theme()`, nothing hardcoded), plus an explicit top-right toggle (system/light/dark) — confirmed live.
- Added real percentage measurements to close a previously-deferred gap: `memory.used_percent` (computed in the existing `free` one-liner) and `cpu.usage` (via `vmstat 1 2`'s second, steady-state sample — a stateless collector trick, no two-cycle delta logic needed in the engine).
- **The GUI no longer decides what a measurement looks like — the metric YAML does, via a `display:` block** (`metric.Display`/`Scale`/`Widget`, resolved into `state.MeasurementView` by `internal/app`). This directly closes the brief's own principle #6 gap we'd been violating: `view.go` used to branch on `unit == "percent"`/`"load"`/`"bytes"` to pick a widget; now it only ever reads `mv.Widget`/`mv.Primary`/`mv.Scale`, and a measurement with no `display:` block renders as plain text — no guessing, no per-metric GUI code. `display.scale.max_ref` resolves a sibling measurement's live value each cycle (e.g. `used` scaled against `total`), never a hardcoded number.
- Gauge zones (the colored green/amber/red bands on the dial) are **derived from the measurement's own event rules**, direction-aware (above/below) — not a separate config, so they can never drift out of sync with what actually alerts. `state.ResolveZones` is pure and unit-tested for both directions against the two real production cases (disk-style above, memory.available-style below).
- Tooltips: compact/medium-tier dots (which show no text label at all) carry a generic `shortAbbrev` (first 3 letters, upper-cased — no per-metric name table) plus the stale reason when applicable.
- Stale rendering fixed: a stale metric used to short-circuit to a bare error line; it now keeps rendering its last-known gauges/bars/values, just in grey, with the reason in the dot's tooltip. Proven through a full success → induced-failure → grey (value preserved) → recovery cycle live, against a throwaway local SSH fixture (not the real lab servers), fully torn down after.
- **A 4th tier — master-detail at ≥700px** (`cmd/watchtower-gui/panel.go`): a compact, clickable server/cluster list on the left (`ui.Split`, draggable divider) and one server's full detail on the right, decluttering what "detailed" became once several servers each had several metrics stacked in one long scroll. Selecting a server is a click (`.Clicked()`/`.Selected()`-style highlight on a plain row — no special list widget needed), not scrolling to find it.
- Right pane is itself splittable (`ui.SplitVertical`, also draggable) — opens an **events/alerts panel** for the selected server, real data (`event.Engine.History()` filtered by server, most recent first), not a placeholder: this is a first real slice of the brief's "full investigation view," built without needing Phase 3 storage at all. Confirmed live: split renders, selection switches the detail pane, events panel opens/closes and lists real events.
- **Real interactive SSH terminal added** (not planned this round, turned out to already exist as `github.com/egoist/mygo/plugins/terminal` — checked before promising it, same discipline as everything else here): toolbar `›` button opens a working shell on whichever server is selected, over its *existing* persistent SSH connection (`sshmgr.Client.OpenShell` — `RequestPty`+`Shell`, wrapped as the `io.ReadWriteCloser` the terminal plugin wants, plus a `Resize` method it type-asserts for), not a fresh re-authentication or a shelled-out `ssh` subprocess. Only ssh-type servers get a working button (`local` servers have no remote session to open — `internal/app.Shells` only contains ssh-type entries); the button disables itself and says why via tooltip otherwise. The terminal engine (`libghostty-vt`, native, built in Zig) is loaded dynamically rather than via cgo — the same reason the rest of MyGo avoids cgo: it's what lets `make build` cross-compile the Windows `.exe` from this Linux box at all. Checked both paths rather than assume: plain `go run`/`go build` (dev-mode, what we live-tested with) fetches it to `~/.cache/mygo/natives/` lazily, at runtime, the first time any terminal opens on that machine — confirmed real but acceptable. The actual packaged build (`make build` → `mygo build`) fetches it **once, at build time**, and bundles it as a plain file next to the exe instead (confirmed: `dist/windows-amd64/ghostty-vt.dll`) — an end user running the real distributed `Watchtower.exe` never touches the network for this at all.
- **Embedded in the main window, not a separate one** — `terminal.View` turned out to be a plain `ui.Element` like any other, no window of its own needed. Lives in the same bottom-split slot Events uses (`bottomMode`: `""`/`"events"`/`"terminal"`, one at a time, picked by the toolbar buttons); the session itself (`termSession`/`termConn`/`termServer`) is tracked independently of which server the sidebar has selected, so switching to check another server and back doesn't kill a live shell — only explicitly targeting a *different* server for the terminal closes the old session. Confirmed live against jumpbox: embedded, working, and mode-switching between Events/Terminal in that one slot behaves correctly.
- Metric-history graph/table is still explicitly out of scope (needs Phase 3 storage — `Store` only ever holds the *latest* value), not forgotten.
- Still open per the brief's "full investigation view" list: services/docker/processes/filesystem drill-down views, journalctl/log viewing, connection-status detail.
- **Global toolbar** (`panel.go`'s `toolbar`, called once from `render`): Events + theme now live in one always-visible row at the top, not scattered per-tier — the Events toggle moved out of the master-detail pane's own header, which just drops a "few more buttons soon" into one place rather than hunting for where each one used to live. Uses MyGo's real `ui.Toolbar` (not a plain `Row`) — its buttons get the flat/compact "toolbar button" look (no background until hover) for free, plus an overflow menu once more buttons stop fitting; natural width keeps it flush left instead of stretched edge to edge.
- Toolbar buttons are icon-only now (`icons.go`): bell (events), terminal chevron, sun/moon/monitor (theme, mirrors the actual current source) — plain monochrome SVGs (`ui.MustParseSVG`, `stroke="currentColor"`, same convention MyGo's own built-in search icon uses), not a borrowed icon font/pack. No built-in icon library exists in MyGo, checked before writing these by hand. Text moved to tooltips instead of sitting on the button.
- Redraw is a 1s polling ticker (`win.Update(func(){})`), not real change notification — fine for a PoC at this scale, worth revisiting if it ever matters.
- Value formatting (`formatValue` in view.go) is still a hand-rolled, bytes-only special case, separate from the widget-selection work above — a real unit-aware formatter is a natural next piece of the same "display hints" idea.
- **Closed: bars now get zone bands too**, same mechanism as the gauge (`internal/app` resolves `Zones` for `WidgetBar` as well as `WidgetGauge`; `bar()` draws colored segments + a marker line instead of a flat fill when zones are present). Confirmed via a new `internal/app` test (`used` — a bar — gets the same zones a gauge would) and live.
- **Closed: `load1`/`load5`/`load15` no longer hardcode `max: 4`.** `cpu.yaml` now collects a `cores` measurement (`nproc`) and the load bars scale against it via `display.scale.max_ref: cores` — the exact same generic mechanism `memory`'s bars already used for `total`, zero new Go code. Confirmed live: jumpbox (8 cores) and sbnats (2 cores) visibly scale differently for similar raw load values.
- **GUI now groups servers by cluster** (`server.Config.Cluster`, a generic free-form label, not NATS-specific; `state.Store.SetCluster` / `ServerView.Cluster`). A cluster renders as a header (rolled-up worst-of-members status, same rule `Store` already applies across one server's metrics, exported as `state.Worst`) with each member indented beneath via the exact same `serverRow` every standalone server uses — "look at the cluster" and "look at one member" are the same view, just how far down you read. Confirmed live with 2 real clusters.
- **Collector commands are now parameterized templates** (`metric.Collector.Render`, Go `text/template` against the fully-resolved group/server `config` map — the brief's own illustrative `metrics.nats.config.endpoint` example, finally implemented). `Definition.Validate` parse-checks the template at load time; a server missing a required config key fails loudly at run time (`missingkey=error`), never silently. `internal/app`'s `effective()` was silently discarding this resolved config before — now it's wired all the way through to `collect.Execute`.

## Phase 7 — Per-server dashboards (widget grid) ✅ done

- User request, explicitly modeled on the author's own NanoTDB dashboard (read `~/code/nanotdb/docs/DASHBOARD.md` before designing, not guessed): decouple "what's on screen" from metric.Display's auto-rendering. A server composes its own grid of widgets — chart/gauge/number/pie — each one naming which metric+measurement(s) to show, independent of whatever that measurement's own YAML display config says.
- **New `internal/dashboard` package** — `Widget{Type, Title, Series}`, `SeriesRef{Metric, Measurement, Label}`, per-type shape validation (gauge/number need exactly 1 series, pie needs 2+, chart needs 1+). A series only ever names a metric+measurement, never a server — the server is already implied by whichever server's config the widget lives in.
- **Config lives in the server's own YAML, not a separate file** (explicit user call, overriding my own first-draft suggestion of a standalone `data/dashboard.json`) — `server.Config.Dashboard []dashboard.Widget`, config-as-code exactly like `Groups`/`Metrics` already are. Hand-editable and GUI-editable are the same file, never two sources of truth.
- **`server.SaveDashboard`** writes GUI edits back to that file — deliberately a surgical `yaml.Node` edit of just the `dashboard:` key, not `yaml.Marshal(cfg)` wholesale: several real server files (`sbnats-nats2/3/5/6.yaml`) have hand-written comments explaining placeholder monitoring ports, and a full struct remarshal would silently destroy them. Proven with a dedicated test that writes a file with a comment, saves a dashboard change, and confirms the comment survived. **Known limitation, found live, not fixed:** the Node-based re-encode does preserve comments but does *not* preserve blank lines between sibling top-level keys (blank lines aren't part of the YAML comment/node model) — a saved file's sections end up adjacent instead of blank-line-separated. Cosmetic, not a data-loss issue; worth a follow-up if it bothers hand-editing.
- **GUI**: toolbar gained a 4th button (reusing `chartIcon`) toggling `showDashboard`, which swaps the detail pane's top content — the per-metric list (`metricLine` by `metricLine`) vs. the selected server's widget grid — independent of `bottomMode` (events/terminal/ad hoc chart keep working in the bottom split either way, per the user's explicit "replaces the right pane" scope decision).
- Widget grid is `ui.Row.Wrap()` of fixed-size tiles (one size for v1, "will be simple" was the explicit brief — no per-widget resize/reorder) — reflows by width same spirit as the window's own breakpoint tiers, just one level down.
- Four tile types: **chart** reuses the exact dual-axis/grid-line/legend renderer built for the ad hoc single-metric chart — extracted into a shared `renderSeriesChart(c, history, title, []chartItem)` so both call sites draw identically, not two copies drifting apart (`chartItem` carries an explicit `historyKey` now, not a naming-convention derivation, specifically so a dashboard chart's series can each name a different metric). **gauge** reuses `pressureGauge`, but only when the measurement's own `Display.Scale` already resolved one — a dashboard widget never invents a scale, it degrades to a plain message instead ("no scale configured for this measurement"). **number** is a plain big-text value tile. **pie** is new: `buildPieSlice` (gauge.go's `buildArc` adapted into a closed, fillable sector instead of an open stroked band), proportion-of-total across the widget's series — real use: a docker metric's running/paused/stopped container counts as slices of a whole.
- **Add/remove, no manual YAML editing required**: a "+ Add widget" tile opens a modal (`ui.Modal`/`ui.Select`/`ui.TextInput`) — pick a type, an optional title, and series from whatever that server is *currently reporting* (`availableSeries`, resolved off the live snapshot, same "no guessing, read real data" rule the ad hoc chart already follows) — confirming calls `server.SaveDashboard`. Each tile's own `×` removes it the same way. Confirmed live end to end: added a chart widget (cpu load1+load5), confirmed it rendered and appeared in `data/servers/jumpbox.yaml`'s new `dashboard:` key, removed it, confirmed it was gone from both the UI and the file.
- A series naming a metric/measurement that isn't currently reporting (removed from `metrics/`, or just hasn't collected yet) degrades to a "not reporting" message per tile, never a crash — same stale-but-visible philosophy as everything else in this app.

## Phase 8 — Per-volume disk stats ✅ done

- User request: `disk` reported exactly one mount (configured per-server, documented as "one definition, one mount point" — watching another meant duplicating the whole YAML file). Changed to auto-discover every real mounted filesystem each cycle instead.
- **A real engine capability, not a disk-only hack** — the static assumption broken here was "one metric definition's measurement keys are a fixed, YAML-declared set", which `collect.Execute`/`internal/app` had baked in everywhere. Generalized instead of special-cased:
  - **`metric.Definition.ResolveMeasurement(name)`** — resolves a measurement name against the declared schema either directly (the ordinary case) or, for a dynamically-discovered instance, by matching `name`'s `_<suffix>` ending against a declared key (`"root_used"` → declared `"used"`, instance `"root"`). One declared `total`/`used`/`free`/`used_percent` now covers however many volumes a host has.
  - **`collect.observationsFrom`** now iterates the collector's actual output and keeps whatever resolves (directly or by instance), instead of only ever emitting literal declared keys — same "unknown keys ignored" contract as before (confirmed unchanged via the existing `extra=999 ignored` test), now also catching instance-prefixed ones.
  - **`internal/app.MetricTask.Run`** scopes `display.scale.max_ref` per instance (`root`'s `used` scales against `root_total`, not a global/`data`'s `total`) and annotates `display.label` with the instance (`"Used" → "Used (root)"`) so the plain metric-line view (no dashboard needed) still tells volumes apart.
  - **`event.Engine.EvaluateThreshold`** gained a second key: `measurement` (alarm identity — each volume gets its own independent hysteresis state, `disk.root` alarming never touches `disk.data`) vs. `ruleKey` (which declared rule set applies — one `used_percent` rule now governs every volume). All 17 existing call sites plus a new one updated/added; proven with a dedicated test that one instance can be critical while a sibling instance stays normal, evaluated through the exact same Engine.
- **Mount sanitization** (`/` can't appear in a measurement name — it's `internal/storage`'s own server/metric separator): `/` → `root`; anything else strips the leading `/` and joins the rest with `_` (`/mnt/disk001` → `mnt_disk001`). Verified directly over SSH against both real servers before writing the YAML, not assumed: jumpbox has 5 real volumes (`root`, `boot`, `boot_efi`, `mnt`, `mnt_disk001`), sbnats has 4.
- **No single "primary" gauge anymore** — `used_percent` dropped `primary: true` (there's no one obviously-headline volume once a host can have several; `display.widget` changed from `gauge` to `bar`, same even treatment every volume gets for `used`/`free`).
- Data reset, deliberately (explicit user call, not a migration): old `data/storage/` held the previous flat `total`/`used`/`free`/`used_percent` keys, incompatible with the new per-volume scheme — cleared rather than migrated.
- Confirmed live against both real servers: jumpbox and sbnats both show every real volume, correctly named, correctly scaled per-instance.
- **Dashboard widgets already supported mixing series from different metrics in one widget** (chart or pie) — not a new feature, just confirmed: `availableSeries` was already built off the whole server snapshot (every metric's measurements together), not scoped to whichever metric a prior pick came from. Verified live with a widget mixing `disk.*` and `memory.*` series.
- **Closed: the dashboard became a real grid, and a chart gets a real 2x2 span.** The widget grid was a wrapping row (`ui.Row.Wrap`) of uniform tiles — fine for gauge/number/pie, but a chart squeezed into the same cell had its axis labels, legend and title crowding out the actual plot (caught live, from a real screenshot, not a layout guess). Checked whether mygo's `ui.Grid` supports spanning before assuming it didn't (read `ui/grid.go`/`api_gen.go` directly): it does — `ColumnSpan`/`RowSpan`, real CSS-grid-like placement, children "fill its cells row by row" by default. Switched `dashboardGrid` to `ui.Grid` with explicit `Fixed(tileWidth)` column tracks (count computed from the actual right-pane width, now threaded down from `render`'s own `c.Size()` rather than guessed), and gave chart tiles `ColumnSpan(2).RowSpan(2)` (`chartSpan` const) sized to exactly match 2 cells + the gap between them — no stretch ambiguity from `Fr`-based tracks.
- **Also tightened the chart's own typography/padding independent of tile size** (the user asked for this in case grid-spanning wasn't available, and it was worth doing either way): `renderSeriesChart`'s title row is now skipped entirely when the title's empty (a dashboard chart tile already shows its title in `widgetCard`'s own header — the old code still rendered an empty, padded row above the legend regardless, wasting vertical space for nothing); axis tick labels got an explicit `FontSize(9)` (previously unset, silently inheriting a larger ambient size — the real cause of "too-large y-axis labels"); legend and plot paddings/gaps trimmed down to match the rest of this app's compact 9-11px UI instead of the looser spacing a full-width ad hoc chart panel could afford.
- Confirmed live: a chart tile is now clearly bigger than a gauge/number/pie tile, the plot has real room, and the axis/legend text no longer crowds it.
- **Closed: per-widget maximize/restore.** Every tile's header got a second icon button (new `maximizeIcon`/`restoreIcon`, hand-drawn to match the rest of `icons.go`) alongside its existing `×`: clicking it fills the whole right pane with that one widget — `dashboardGrid` skips the grid and the "+ Add widget" tile entirely while one's maximized, rendering just that tile in a plain `Box.Fill()` — and clicking again (now showing inward arrows) restores the full grid. Gauge/pie tiles also draw their dial/pie larger when maximized (240/220 DIPs vs. the tile-sized 100/90) rather than just centering in empty space; the chart tile already fills whatever box it's given. State (`maximizedServer`/`maximizedIdx`) is keyed by server name, not just index, specifically so switching the sidebar's selection while one widget is maximized can't leak a stray maximized tile onto an unrelated server that happens to share the same widget index — confirmed live.
- **Closed: widget span is configurable, not hardcoded to "chart = 2x2, everything else = 1x1".** User question: "are charts ALWAYS 2x2 spans? we should have that configurable." `dashboard.Widget` gained `Span int` (`yaml:"span,omitempty"`, 0-3, 0 meaning "this type's own default" — `Widget.EffectiveSpan()` resolves it: 2 for chart, 1 otherwise, same as before when left unset). An explicit `Span` overrides either direction — a one-line chart can be made smaller, a single gauge can be made bigger. `cmd/watchtower-gui/dashboard.go`'s tile sizing was generalized to match: `widgetCard` takes a `span` (not raw pixel w/h) and centrally chains `ColumnSpan`/`RowSpan`, so every widget type (not just chart) can span cells; gauge/pie/number also scale their drawn content (dial diameter, pie diameter, number font size) with the span, not just when maximized. The add-widget modal gained a "Size" picker (Auto/1x1/2x2/3x3). Confirmed live: Auto still gives a chart its old 2x2, an explicit 2x2 gauge/number is visibly bigger than default, and an explicit 1x1 chart is visibly smaller than its default.
- **Closed: bigger pie/gauge/number tiles, and a width-aware gauge label fit.** Real screenshots showed a pie and gauge both with a small graphic swimming in empty tile space, and the number widget's text too small. Base sizes bumped (gauge diameter 100→140, pie diameter 90→130, number font 28→40, each still scaling further with `Span`/maximized), and the pie's legend gap widened (10→24) per the user's "move labels more to the right". That first pass immediately exposed a real, caught-live regression: `pressureGauge`'s center label was sized as a flat `diameter*0.22`, tuned for short "42%"-shaped labels — at the new diameter, a longer dashboard-formatted value (e.g. "23.6GiB") visibly overlapped the ring. First attempted fix (measuring against 80% of the *outer* diameter) turned out barely different from no fix at all once actually screenshotted. The real fix (`centerLabelFontSize`, gauge.go) measures against the ring's own *inner* diameter (`diameter - 2*stroke`, since that's the circle the text actually has to fit inside) with a tighter per-character width estimate tuned for `Bold()`; confirmed live after the correction, not after the first attempt — a reminder that "looks right in the formula" and "looks right on screen" aren't the same check.
- **Closed: per-series printf-style `Format`.** `dashboard.SeriesRef` gained `Format string` (e.g. `"%.0f"`, `"%5.2fGb"`, `"%6.2f%%"`) — a dashboard-only override that always wins over the automatic unit/`display.format`-driven rendering, for whenever a widget wants a value shown exactly one specific way. `applyFormat` (cmd/watchtower-gui/dashboard.go) special-cases integer verbs (`d`/`b`/`o`/`x`/`X`/`c`) by rounding to `int64` first — `fmt.Sprintf("%d", 23.6)` would otherwise print Go's own ugly `"%!d(float64=23.6)"` instead of a number. `seriesValue` picks `ref.Format` when set, else falls back to the existing `formatValue`. Exposed in the add-widget modal as a "Format (optional)" field for gauge/number (single-series types only — pie/chart's several series have no per-item editor yet, hand-edit the YAML's `series[].format` for those). Confirmed live.
- **Closed: widgets are now editable, not just addable/removable.** A new pencil icon (hand-drawn `editIcon`, same convention as the rest of `icons.go`) sits in every tile's header alongside maximize/remove. Clicking it opens the same add-widget modal, pre-filled from that widget's current Type/Title/Span/Series/Format (`openWidgetEditor`) — one modal and one `confirmAddWidget` for both flows, not a second editor built separately; `confirmAddWidget` replaces the widget at its original index in place when editing (`editWidgetIdx >= 0`) instead of appending a duplicate. The modal's own title and confirm-button label ("Edit widget"/"Save" vs. "Add widget"/"Add") track which mode it's in — caught live that the button still said "Add" while editing, fixed on the spot. Adding a third header button meant shrinking all three (`headerButtonSize` const, 11→9) so they'd still fit without crowding the title on a normal-width tile. Confirmed live end to end: edit pre-fills correctly, Save replaces in place, and both button labels are correct in their respective modes.

## Phase 9 — Storage durability tuning, and the dashboard becomes the only view ✅ done

- **Storage: periodic sync, not per-write fsync.** User report: "the storage data files for yesterday are gone." Checked `internal/storage/store.go` before assuming a bug — it already appends (`O_APPEND`, never rewrites), already fsynced every write, and retention was 30 days (nowhere near deleting a 1-day-old file). The real cause, found by checking `data/storage/`'s actual state: it didn't exist, and was gitignored (no recovery path) — I had run `rm -rf data/storage` as a "clean slate" step dozens of times this session's own live-proof cycles, which is what actually wiped it. Said so plainly rather than inventing a fix for a bug that wasn't there, and stopped doing it as a routine step.
- Separately, asked for and implemented a real change: `Append` no longer fsyncs every write — it syncs on whichever comes first of `syncEvery` (50) writes or `syncInterval` (15m) of wall-clock time, with `Close()` and a day's partition rolling over always syncing unconditionally regardless of those thresholds (`closeOpenFileLocked`, since `Close(2)` alone doesn't guarantee the OS page cache was flushed — only an explicit `Sync` does). New tests cover the count threshold, the interval threshold (via an injectable `now func() time.Time`), and the real-world guarantee: a write below both thresholds still survives a `Close`+reopen.
- **Found and fixed a related real gap while testing this**: `cmd/watchtower-gui/main.go` only trapped `SIGINT` (Ctrl+C), not `SIGTERM` — the signal a plain `kill <pid>` sends by default, which was this session's own entire test-cleanup methodology throughout. An uncaught `SIGTERM` skips `main()`'s deferred `history.Close()` entirely, meaning every single prior test-cleanup kill this session bypassed the sync-on-shutdown path. Added `syscall.SIGTERM` to the trapped signals. Proven live, not just argued: launched a fresh instance, let it collect a handful of points (nowhere near either sync threshold), sent a plain `kill`, confirmed the process exited, then queried the reopened store with a throwaway inspector program and confirmed every point — including the very last one collected — survived.
- **Closed: the old per-metric list pane is gone, the dashboard is the only view, at every window width.** User: "we still show the old metrics pane in the right pane when we resize the window... dashboard is what we need to show by default." `render()` no longer branches on a `breakpointWide` width check — it always calls `renderMasterDetail` (sidebar + that server's own dashboard), regardless of how narrow the window gets. This made a chain of other code genuinely unreachable, removed rather than left as dead weight: the three width-tiered stacked rendering functions (`serverRow`, `clusterRow`, and the `compact`/`medium`/`detailed` breakpoints), `metricLine` (the per-metric auto-rendering those tiers used), and — since `metricLine`'s inline chart-icon button was the *only* thing that ever set `chartServer`/`chartMetric` — the entire ad hoc single-metric chart feature (`chartPanel`, the `bottomMode == "chart"` case) it drove, now permanently superseded by per-server dashboards anyway. Also removed with it: `bar`/`barEntry`/`percentLabel` (gauge.go) and the unused `chartIcon`, which had no other callers once `metricLine` was gone. `groupByUnit`/`chartItem`/`renderSeriesChart`/`seriesColors`/`chartWindow` all stay — the dashboard's own chart tile still depends on them.
- **Known, accepted consequence, not hidden**: `metric.Display.Widget` values `bar` and `dot` no longer have any auto-rendered view anywhere in the GUI (only `gauge`'s `Scale`/`Zones`/`Primary` resolution still feeds something visible, via a dashboard gauge widget). A metric's `display:` block still matters for *validation* and for what a dashboard gauge/bar-shaped widget can show, but nothing auto-renders it without an explicit dashboard widget pointed at it anymore — the natural end state of "decouple metrics from charts," not an oversight.
- Confirmed live: resizing the window to any width, including quite narrow, keeps the dashboard showing — no fallback to the old pane.
- **Closed: drag-and-drop to reorder dashboard widgets.** User asked tentatively, expecting a "not worth it" answer — checked mygo's actual API first rather than guessing it'd be painful: it has real generic drag-and-drop built in (`Element.Drag(value)` as a source, `ui.DragOver[T]`/`ui.Drop[T]` as a typed target, confirmed by reading `draggable.go`/`api_gen.go` before committing to the feature), which fit directly onto the existing per-tile chrome with no custom pointer-tracking needed. Each non-maximized tile in `widgetCard` is now both drag source and drop target, carrying its own index as a small named type (`dragWidgetIdx`, not a bare `int` — so this pairing can't accidentally match some unrelated int-carrying drag elsewhere) — a border highlight while a compatible drag hovers over a tile, and dropping calls `reorderWidget` or moves that widget to the drop target's slot, persisted via `SaveDashboard`.
- **A real bug caught by `reorderWidget`'s own test, not live**: the first version applied a direction-dependent index shift ("subtract one if moving later") reasoning from "insert before the target" semantics; the actual desired behavior is "end up in the target's slot" semantics, which needs no direction-dependent adjustment at all — inserting at `toIdx` into the already-one-shorter slice (after removing the dragged element) lands it at index `toIdx` of the result regardless of which direction it moved. `TestReorderWidget` covers both directions plus drop-on-self and out-of-range as no-ops.
- Confirmed live end to end, including real on-disk evidence, not just a visual check: dragging "Memory Free" from 1st to 3rd on jumpbox's real 5-widget dashboard produced the exact reordering in `data/servers/jumpbox.yaml`'s `dashboard:` list.

## Phase 6 — Expand the monitoring library 🟡 started

- Have: `memory` (full, incl. `used_percent`), `cpu` (load averages + real `usage` % via `vmstat`), `nats` (connections/msgs/bytes/slow_consumers/mem/cpu via its HTTP `/varz` monitoring endpoint — now a native Go collector, see below, not shell+curl+jq).

The other 4 are modeled with placeholder ports and correctly show stale/critical until monitoring is enabled on them server-side — not something this app can or should fix.
- Along the way: caught and fixed a real bug in the first (shell-based) version of `nats.yaml` before it shipped — a bare `curl | jq` pipeline reports jq's exit code, not curl's, so a down endpoint would've looked like a *successful* collection with zero measurements. Also verified, on request, that `jq` simply being absent already fails safely on its own (it's the pipe's last stage, so its own "command not found" is the real exit code) — no code needed for that one. Both are moot now that `nats.yaml` doesn't use a shell at all.
- **Added `disk`, `network`, `systemd`, `docker`** (`metrics/linux/`, `metrics/services/` — the brief's own directory layout). All plain shell/awk, no new dependencies. Missing still: mqtt, postgres.
  - `disk`/`network` ship a **collector-level default config** (`disk.path: "/"`, `network.iface: ""` meaning auto-detect via default route) — a new small piece of `metric.Definition.Resolve`: config now seeds from the collector's own default *before* group/server overrides apply, so a server only needs to say anything when it wants something other than the sensible default. (`nats`'s `endpoint` still has no default — there isn't a sane universal one.)
  - `systemd` needs an explicit `config.unit` per server (no default makes sense); its `active`/`enabled` measurements are the first real use of `display.widget: dot`, which turned out not to be rendered at all in the GUI yet — closed that gap too (`cmd/watchtower-gui/view.go` now has a dots branch: colored dot + label, no `=value` text, as the widget's own doc comment always said it should be).
  - `docker` deliberately avoids `docker info --format '{{...}}'`: that's Docker's *own* Go-template syntax, which collides with this engine's command templating (same `{{ }}` delimiters) — tried it, confirmed the escape-dance technically works, decided it was needlessly obscure, used plain `docker info` text parsed via `awk` instead, consistent with every other metric here. Only `jumpbox` gets the `docker` group — confirmed live `sbnats` has zero `docker.*` output.
  - `network`'s `rx_errors`/`tx_errors` events are an honest, flagged trade-off: they're cumulative counters, not a per-interval rate (no counter-delta support in the engine yet), so "above 0" warns once and then never recovers. Documented in the YAML itself, not hidden.

## Transports ✅ SSH + local, plus a native HTTP/JSON collector

- **`server.Connection.Type: local`** — a second transport alongside SSH, for endpoints reachable directly from wherever Watchtower runs (no SSH hop needed). `internal/localrun.Runner` runs shell collector commands via `sh -c` on the local machine.
- **`collector.type: http`** (the main item this round) — a native Go collector: fetches a URL and JSON-decodes it in-process, no curl/jq/shell anywhere, on any platform. `collector.fields` maps a measurement key to a JSON field (dot-path for one level of nesting); omitted entirely when names already match, as `nats.yaml` now does.
- The interesting part: an `http` collector still needs to reach a **loopback-bound** endpoint on a remote host (exactly our real NATS case — `localhost:8222` only means anything from sbnats's own perspective). Solved by adding `DialContext` to both backends: `sshmgr.Client.DialContext` tunnels the TCP connection through the *existing* SSH session (`ssh.Client.Dial`), so the request reaches the target exactly as if curl were running on that host — `localrun.Runner.DialContext` just dials directly for a `local` server. `collect.Runner` (shell) and `collect.Dialer` (http) combine into `collect.Backend`; `MetricTask.Client` holds one `Backend`, and `collect.Execute` dispatches on `Collector.Type` to decide which half it actually needs.
- Proven live against the real, previously-problematic case: `nats1`/`nats4` (loopback-bound, on sbnats) returned full real data over the SSH-tunneled native HTTP path; `nats2/3/5/6` (still unmonitored) failed with `ssh: rejected: connect failed ("Connection refused")` — the SSH protocol's own channel-open rejection, proving the tunnel itself works, not just that failures are masked. Confirmed the GUI renders identically — the collector changed underneath, presentation didn't need to know.
- **`display.label`** — a measurement's own key is often just whatever its source calls it (a JSON field name, say) rather than something you'd want to read in a control room. Optional, generic (not HTTP-specific — any measurement can set it), falls back to the key when unset (`state.MeasurementView.DisplayLabel()`, one rule every presentation applies instead of each re-checking "is Label empty" itself). `nats.yaml` now labels every field ("Connections", "Memory", "CPU", ...); confirmed live.

## Other deliberately deferred / known limitations

- **SSH reconnect has no backoff** — `sshmgr.Client` redials immediately on the next use after a dropped connection; fine at this scale, would hammer a genuinely down server at larger scale.
- **Concurrency cap is a hardcoded const** (`maxConcurrentCollections = 16` in `main.go`), not exposed as config yet.
- **No credentials beyond SSH key file / ssh-agent** — satisfies "no plaintext passwords," nothing fancier (vault, etc.) built or asked for.
- **No SSH connection sharing across server entries on the same host** — `sbnats`'s 7 server configs (1 OS-level + 6 NATS processes) each open their own independent SSH connection to the identical machine. Simple and correct, but observed a real (self-recovering) transient timeout during the initial connection burst with 7 at once; worth revisiting if a host ever hosts many more monitored processes than that.
